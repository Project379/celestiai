## 1. How complete is web, on its own terms

Web is substantially more finished than a "reference implementation with holes" framing suggests — every step of the golden path is real, not stubbed, down to the database writes. Sign-up is lazy: there is no Clerk webhook (`apps/web/app/api/webhooks/` holds only `stripe` and `revenuecat`), so the `users` row is created on first authenticated write via an upsert in `packages/core/src/charts/birth-data.ts:70-75` and `apps/web/lib/users/ensure-user.ts:54-111`; this works safely because the database itself defaults `subscription_tier` to `'free'` (`supabase/migrations/20260413141504_schema_hardening.sql:59-60`), so a bare upsert never leaves a user in an invalid state. Birth data entry is real end to end: `BirthDataWizard.tsx:89` posts to a validated API route, city search hits a real `bulgarian_cities` table, and the result persists verbatim into `charts`. The natal chart is a genuine Swiss Ephemeris calculation via `packages/astrology`'s `sweph` binding, cached in a `chart_calculations` table, with no mock data path anywhere in the render chain. The daily horoscope is generated live per-request against OpenRouter (Llama 3.3 70B) when a user visits the dashboard — worth correcting an assumption baked into the original ask: the daily-horoscope cron job does **not** generate content, it only fires a generic push-notification nudge (`apps/web/app/api/cron/daily-horoscope/route.ts:13-15` says so explicitly in a code comment); actual generation happens in `useDailyHoroscope` → `/api/horoscope/generate`. The Oracle is likewise fully wired — 12-step flow with auth, ownership checks, a 24-hour regen cooldown, monthly quota enforcement with refund-on-failure, and real LLM streaming — it just isn't a dedicated page; it's a global panel mounted in the protected layout and opened by a custom event. Кръг is real too: invites, space membership, and relationship reports all compute genuine cross-chart compatibility via `packages/core/src/relationships/compatibility.ts`, rendered into Bulgarian prose through deterministic score-band templates rather than an LLM call (a design choice, not a shortcut). Stripe subscribe/cancel is fully wired with webhook signature verification, idempotency via a `processed_webhook_events` table, and a second, correctly-guarded fast path that activates premium immediately from a verified Checkout session rather than waiting on the async webhook.

Two things are genuinely unfinished and worth flagging plainly rather than softening. First, Bulgarian LLM output quality has **zero corrective mechanism**, by explicit written instruction in the code: `apps/web/lib/ai/client.ts:9-13` states the model is "a known-weak-Bulgarian placeholder" and that the team should *not* add retries or post-processing to compensate; the only quality signal is a fire-and-forget Hunspell check that logs flagged words to a table nobody currently alerts on, and if the dictionary file it depends on isn't present in the serverless bundle, that signal silently goes dark. This is the single largest quality risk in the product today, by design, pending the external model-replacement research the founder mentioned. Second, error/empty-state handling is `[inferred]` incomplete: `apps/web/app/(protected)/dashboard/page.tsx:28-50` swallows fetch failures into `console.error` and falls through to the same "no data yet" UI used for genuinely empty accounts, and there is no segment-level `error.tsx` anywhere under `(protected)/**` — only the root `global-error.tsx` — so a mid-journey API failure and an empty account look identical to the user. Beyond those two, and the lint/test gaps already noted in §0, web holds up as a real, working product on its own terms — the "web is the finished reference" premise is largely correct, not a story that collapses on inspection the way PostHog/RLS/parity claims did earlier this session.

## 2. How far behind is mobile, feature by feature

Parity is closer than the founder's framing implied, with one real, large exception and one smaller, cleaner one. Birth data entry, chart display, daily horoscope/rhythm, Oracle, journal/diary, crystals, push notifications, GDPR export/delete, and identity settings are all **at parity** on mobile — each is backed by a real hook calling a real API route, not mock data, verified by reading the hook files and confirming `apiFetch` calls into the same endpoints web uses. One architectural note worth correcting in CLAUDE.md: it states mobile visualization uses React Native Skia and web uses D3+Canvas; in practice both natal-chart wheels are SVG-based (`react-native-svg` on mobile, d3-driven SVG — not Canvas — on web). No Skia dependency exists anywhere in the mobile app (`AmbientBackground.tsx:11` even has a comment noting Skia is unavailable under the current build constraint); this is a documentation-vs-code discrepancy the doc should be corrected against, not a functional gap.

Кръг is the real gap, and the founder's "70-line static empty state" description checks out exactly — `apps/mobile/app/(authed)/(tabs)/circle.tsx` is precisely 70 lines, three `Pressable` cards with no `onPress` handlers and no data calls anywhere in the mobile codebase. But the scope of closing it is smaller than the Skia framing implied: the web `CircleHub.tsx` (936 lines) has **zero** D3/Canvas/SVG usage — it's forms, lists, and cards — so porting Кръг is a matter of building new React Native screens against the nine existing, platform-agnostic API routes, not a visualization rewrite. The compatibility-math core (`packages/core/src/relationships/compatibility.ts`, 548 lines) is already shared and importable by mobile as-is. What's missing is purely the ~1,200 lines of client-side UI (`CircleHub.tsx` + `SavedProfileForm.tsx`) that has no shared-package or mobile equivalent today.

The second confirmed gap is subscription/paywall management: `apps/mobile/app/(authed)/you/premium.tsx` is a literal 45-line "Премиум идва скоро" ("Premium coming soon") stub, and `RevenueCatProvider.tsx` only wires identity (`configure`/`logIn`/`logOut`) — its own code comment states "No offerings/purchase/entitlement reads here," and it's running with a placeholder API key. Web's equivalent surface (checkout, portal, cancel, status display) is ~430 lines across `AccountSubscriptionPage.tsx` and the subscription portion of `SettingsContent.tsx`. This is a full gap, not partial credit — mobile currently has no way to purchase, view, or cancel a subscription.

## 3. What's missing from both platforms

Confirmed absent everywhere: **transactional email**. No email SDK (Resend/SendGrid/Postmark/Nodemailer/SES) exists anywhere in the monorepo — grepped every `package.json`, zero hits. This means the GDPR-deletion-confirmation email the founder listed as a founder-track blocker has no delivery mechanism to build on yet; Clerk sends its own auth emails (verification codes etc.), but that's Clerk-managed and doesn't cover app-originated messages like deletion confirmations or receipts. Also confirmed absent: **mobile offline handling** — zero NetInfo usage, no offline queue, no cache-first strategy; the app assumes live network everywhere. **Password reset on mobile specifically** is missing — mobile auth is fully custom-built on Clerk's `useSignIn`/`useSignUp` hooks (not Clerk's prebuilt UI), and there is no forgot-password screen or link anywhere in `(public)`; web gets this for free via Clerk's stock `<SignIn>` component. `.planning/REQUIREMENTS.md:22` marks password reset "complete," which is true for web and stale for mobile — a doc that needs a mobile-specific correction, not a wholesale rewrite.

Rate limiting is real but narrower than the "table-backed rate limiting" description suggests: the implementation itself (`apps/web/lib/rate-limit.ts`, Supabase RPC-backed, fails open, real 429s) is solid, but of 34 API route files only three actually call it — `cities/search`, `horoscope/generate`, `oracle/generate`. Several unprotected endpoints carry the same abuse-cost shape those three were built to guard against, notably `circle/*/report` and `circle/*/weather` (each triggers a real ephemeris calculation plus template generation) and `diary/entries` — these are gaps worth closing before any paid or public traffic, not hypothetical hardening.

GDPR export/delete are real, not stubs, on both platforms — verified by reading the route handlers, which touch 9+ tables for export and implement a genuine 30-day soft-delete/grace-period/cancel cycle with audit logging, consumed by both a web route and a dedicated mobile hook (`useAccountDeletion.ts`). What's missing there is narrower than "GDPR incomplete": no cookie-consent mechanism exists anywhere on web (zero "cookie" string in the privacy page or codebase), and no documented data-retention policy file exists in `.planning`.

## 4. Port backlog, ordered

This section is my own synthesis from the evidence above, not delegated — it requires prioritization judgment. LOC bands are measured from the actual web counterparts (`wc -l`), with the founder's own stated multipliers applied: **+25-30%** for work with an existing pattern to follow, **+50-70%** for first-of-its-kind work on a platform. These are LOC-effort bands, not time estimates — translating to calendar time is part of §8, and depends on who does the work.

1. **Кръг port (blocked on nothing, ready to start).** Base UI surface to replicate: `CircleHub.tsx` (936) + `SavedProfileForm.tsx` (278) = ~1,214 lines of web React to re-express as React Native screens. This is first-of-its-kind for mobile (no existing multi-entity list/form/detail pattern at this scale exists in the mobile app yet, unlike e.g. the wizard screens which had a template to extend) — apply the 50-70% band: **~1,800-2,050 LOC of new mobile code**, plus new `apiFetch` client wrappers for the 9 existing circle API routes (thin, low-risk — those routes are already platform-agnostic and don't need touching). The compatibility math and report/weather template logic in `packages/core` and `apps/web/lib/circle/*` need zero changes; mobile calls the same server. This is the single largest, most self-contained port item, and the only one where the founder's own framing (Skia rewrite) turned out to overstate the difficulty — it's forms and lists, not a canvas.

2. **Mobile subscription/paywall UI (blocked on RevenueCat dashboard completion, a founder-track item in §6).** Base web surface: ~430 lines (`AccountSubscriptionPage.tsx` + `SettingsContent.tsx` subscription portion). This is also first-of-its-kind on mobile (no purchase flow exists at all today) but smaller and narrower in scope — RevenueCat's SDK provides prebuilt paywall UI components that can shortcut some of the custom-build cost, so the multiplier should land nearer the low end of first-of-its-kind: **~650-950 LOC**, split between offerings/purchase/restore logic in `RevenueCatProvider.tsx` and a new premium-status/cancel screen replacing the current stub. This is genuinely blocked, not just unstarted: RevenueCat is running on a placeholder API key per its own code comment, so no purchase flow can be tested against real store products until the founder-track RevenueCat dashboard item closes.

3. **Mobile password reset (small, unblocked).** No existing forgot-password screen on mobile; needs one new screen plus wiring into Clerk's `useSignIn` reset-code flow (Clerk supports this without server-side work, just client-side UI/UX). Comparable in shape to the existing `verify.tsx`/`two-factor.tsx` screens (~230 and ~? lines respectively) which are a direct pattern to follow — apply the low, precedented 25-30% band off a ~150-200 line base: **~190-260 LOC.** Cheap, should not wait on anything else.

4. **Rate limiting expansion (small, unblocked).** Extending the existing `apps/web/lib/rate-limit.ts` pattern to `circle/*/report`, `circle/*/weather`, and `diary/entries` — precedented work (the pattern exists in 3 other routes already), 25-30% band, on a base of maybe 15-20 lines per route: **~60-100 LOC total** across three routes. Small but should land before any paid traffic, given those are exactly the AI/compute-cost-risk endpoints the existing limiter was built to protect.

5. **Segment-level error boundaries on web (small, unblocked).** Adding `error.tsx` under the `(protected)` route segments that currently fall through to the generic "no data" UI on fetch failure (dashboard, chart, circle, oracle panel). Precedented — Next.js's own convention, low complexity: **~30-50 LOC per segment**, 4-5 segments.

6. **Transactional email capability (blocks GDPR-deletion-confirmation email, a founder-track item).** No SDK chosen yet — this is a decision point before it's a port item. Once a provider is picked (Resend is the common low-friction choice for a Next.js app), initial wiring (client setup + one deletion-confirmation template) is precedented-elsewhere-but-first-of-its-kind-here: budget the higher band on a small base, roughly **~150-250 LOC** for the first template plus send-on-deletion-request wiring.

Everything above is UI/product work; the amber→bronze color migration and remaining mockup-to-screen ports are scoped separately in §5 since they're design-parity work, not feature-parity work, and the founder was explicit that parity comes first.

Nothing in the code points to an outstanding blocker for the *next* deploy attempt — but since the code passing a local build isn't the same as a live push actually going green on Vercel's infrastructure (the exact "passes locally, fails in CI" pattern that bit this session twice already), this is worth treating as `[inferred, not verified]` until an actual push is watched.

**iOS and Android** are both further behind than build-config-complete: `app.json` reserves bundle identifiers (`com.stellaeum.app` both platforms) but has no `ios.buildNumber`, no entitlements block, no `android.versionCode`, and critically **no `eas.json` exists anywhere in the repo** and no `app.config.js/ts` either. **Domain**: zero wiring found anywhere in code — `NEXT_PUBLIC_APP_URL` still defaults to `localhost:3000` in `.env.example`, and no `stellaeum.com`/`.app`/`.bg` string exists in code outside a Stripe product-name comment. **App icon artwork — remaining piece of the brand-imagery gap** — added 2026-08-05, discovered while debugging the Android EAS build (`.planning/phases/phase-a-mobile-scaffold/REVISIT-TRIGGERS.md` item 67), updated same day once splash and notification icon were fixed with real assets. **Splash and notification icon are done and working** — founder supplied `apps/mobile/assets/splash.png` (solid `#08060f`) and `apps/mobile/assets/notification-icon.png` (a white crescent-moon glyph on transparent), both verified pixel-by-pixel this session (splash: every pixel exactly `#08060f`; notification icon: every non-transparent pixel exactly pure white, no other color) and confirmed rendering correctly in a local prebuild. Different deliverable format from the glyph brief's path-only tintable SVGs either way (the icon needs full color and proper transparency, raster-exportable) — same designer, same commission, not the same file spec.

## 7. Compliance and launch readiness

Apple requires in-app account deletion since 2022 — **this is implemented** (`useAccountDeletion.ts` + `settings.tsx` on mobile, consuming the same real 30-day-grace-period route web uses) and would likely satisfy review on that specific point, pending an actual click-through since no live UI test was possible this session. What's missing for Apple: no `PrivacyInfo.xcprivacy` (required-reason API privacy manifest) exists anywhere under `apps/mobile` — this can block submission depending on which installed SDKs (Sentry RN, Clerk) trigger required-reason declarations, and is worth checking against Apple's current SDK list before assuming it's fine. Google Play's account-deletion requirement is satisfied by the same shared mechanism; Play submission is blocked further upstream by the missing Android EAS build (§6), so the Data Safety form work is premature until a build exists to describe.

GDPR: export and delete are both real, broad implementations (9+ tables touched by export, audit-logged deletion with grace period) — genuinely ahead of what `.planning/PRE_LAUNCH_PREREQS.md` (last reviewed 2026-04-27, three-plus months stale) still lists as "not started." This is a rare case this session where the doc undersold the code rather than oversold it — worth correcting the doc, but in the optimistic direction for once. What GDPR still lacks, confirmed: **no cookie-consent mechanism anywhere** (zero "cookie" string in the privacy page or a dedicated component), and **no documented data-retention policy**. Given the app sets analytics/session cookies via Clerk and Stripe at minimum, a consent banner is a real pre-launch requirement, not a nice-to-have.

Analytics: PostHog remains genuinely uninstalled — re-verified this session (zero package.json hits; the only reference is an explicit future-placeholder comment in `useFeatureFlag.ts`) — confirming the earlier session's finding was correct and hasn't quietly been fixed since. Sentry, by contrast, is genuinely and completely wired on both platforms (`@sentry/nextjs`, `@sentry/react-native`, real DSN env scaffolding, CSP-tunnel route) — this is one of the few "done" claims in `.planning` that fully checks out against code.

The blunt version, for anything that would get a submission rejected outright: no EAS build exists for either mobile platform, so there is currently nothing to submit at all — that is the hard blocker ahead of every other compliance item. Behind that: missing ToS, unconfirmed DPAs, no cookie consent, and a possibly-missing Apple privacy manifest are all real but secondary — they'd surface on review of a submitted build, not before one exists.

## 8. The honest bottom line

This section is my own judgment call, not delegated, per the founder's own standing rule that prioritization work stays in-thread.

The picture that emerges is better than "everything believed was unverified" would predict, and worse than "web is done, mobile just needs to catch up" would predict. Web is real and works end to end on its own terms, with two named, bounded quality gaps (LLM Bulgarian output has no corrective path by design; error/empty states are indistinguishable in a few places) rather than structural rot. Mobile is at genuine parity on eight of ten major features, with exactly two real gaps — Кръг and subscription management — both scoped precisely above and both smaller in code-volume terms than the founder's own framing suggested (Кръг isn't a Skia rewrite; it's ~2,000 lines of forms over API routes that already exist and don't need to change). The CI gate is real and green for what it checks, but "all gates green" quietly excludes `pnpm lint` (currently red, 2 real errors, nothing catches it) and every automated test outside the astrology engine (web/mobile/core have zero). That gap between "CI green" and "actually verified" is the same disease named at the top of this session, just found in a smaller, cheaper-to-fix place than RLS or PostHog.

Split by who can do what: the founder's own track (mobile UI ports, EAS build setup, domain/Vercel/ToS/RevenueCat dashboard work) is long but mostly unblocked and sequenceable — EAS build profiles should move earlier than originally implied, since nothing on the compliance side (Apple/Google submission, Android testing) can even be attempted without one, and it blocks nothing else, so there's no reason it should wait. Petko's track (Кръг backend is done; his remaining scope is largely the co-owned Кръг mobile port plus whatever piece of the amber→bronze/web-redesign work the two of you split) is smaller than mobile's full backlog but not trivial — porting a 936-line hand-built UI component to React Native, even with no visualization complexity, is real first-of-its-kind work for this codebase. Neither of you can move the domain purchase, Apple Developer enrollment, or legal DPA sign-offs alone in the sense that those are external, single-actor gates — but none of them require the other's code to be ready first, so they should run in parallel with the port work, not after it.

What's most likely underestimated, based on what actually surfaced this session versus what was assumed going in: the gap between "CI passes" and "verified" in the testing sense (zero tests outside astrology means every non-ephemeris code path is unverified except by manual read-through, which is exactly the failure mode that produced this whole checkpoint) is probably the largest hidden risk, larger than the named feature gaps. Second: the founder's own "25-30% / 50-70% overrun" pattern applies most sharply to the Кръг port and the mobile subscription UI, both first-of-its-kind on this platform — the LOC bands in §4 already bake that in, but calendar-time slippage on first-of-its-kind work tends to compound past a flat percentage when a second unknown surfaces mid-build (e.g., discovering RevenueCat's paywall SDK doesn't fit the existing design-system primitives cleanly), so treat those two bands as floors, not ceilings. Third, and smallest but real: the Apple privacy-manifest question was flagged, not resolved — worth 30 minutes of direct verification before it becomes a submission-day surprise, since it's cheap to check and expensive to discover late.

No week-count total is given here deliberately: the founder track alone contains at least one item (domain purchase → DNS propagation → Clerk/Stripe prod reconfiguration) with externally-imposed latency that doesn't compress under more hours, and the Кръг/subscription port bands in §4 are LOC, not calendar time, because velocity wasn't measured this session and estimating it now would be exactly the kind of unverified number this checkpoint exists to avoid producing.

### 9.3 Testing gap — proposal, and what got built

Vitest is the established pattern (already used by `@stellaeum/astrology`, 39 tests, `vitest.config.ts` at the package root) — recommend extending the same tool to `apps/web` and `packages/core` rather than introducing a second framework. For Next.js API route handlers specifically, Vitest can invoke the exported `route.ts` handler functions directly with constructed `Request` objects and mocked Supabase/Stripe/RevenueCat clients — no need for a running server or a heavier tool like Playwright for this tier; Playwright/e2e is a separate, later investment for click-through UI flows, not proposed here.

Risk-ranked scope, six areas, sized against the actual file LOC measured this session:

1. **Stripe webhook** (`apps/web/app/api/webhooks/stripe/route.ts`, 153 lines + `apps/web/lib/stripe/subscription.ts`, 464 lines — 617 total). Highest risk: silent failure here means paying users don't get premium, or a signature-check regression accepts forged events. Minimum useful suite: signature verification (valid/invalid/replayed), the four event handlers (`checkout.complete`, `invoice.paid`, `subscription.updated`, `subscription.deleted`) each asserting the correct `subscription_tier` write, the ownership-mismatch guard (cross-account spoofing), and idempotency (same event ID processed twice → single write). **~10-14 test cases, ~350-450 LOC** (webhook payload fixtures are the bulk of the volume here).
2. **RevenueCat webhook** (`apps/web/app/api/webhooks/revenuecat/route.ts`, 148 lines). Same failure mode as Stripe, plus this one already has the most carefully-written code in the repo (HMAC + `timingSafeEqual`, replay window, race-safe idempotent insert) — tests here are as much regression-proofing against a future well-meaning refactor as they are bug-catching today. Minimum: HMAC valid/invalid/tampered, replay-window boundary (in/out of the 300s tolerance), duplicate-event idempotency via the unique-constraint path, fail-closed when secret is unset. **~6-8 test cases, ~150-200 LOC.**
3. **Chart calculation + persistence** (`apps/web/app/api/chart/calculate/route.ts`, 70 lines + `packages/core/src/charts/calculate.ts`, 100 lines — 170 total). Risk: a silent regression here produces a wrong natal chart, which is the entire product. The `@stellaeum/astrology` layer underneath is already validated (39 tests); what's untested is the layer above it — cache-hit vs. cache-miss branching in `chart_calculations`, and that the right birth-data fields flow into the ephemeris call. Minimum: cache hit returns without recomputing, cache miss computes and persists, malformed/missing birth data is rejected before reaching the ephemeris call. **~6-8 test cases, ~120-180 LOC.**
4. **Oracle quota enforcement** (`apps/web/app/api/oracle/generate/route.ts`, 376 lines). Risk: silent failure either lets users bypass their monthly quota (cost exposure on a metered LLM) or wrongly blocks paying users. Minimum: quota-available path claims and increments correctly, quota-exhausted path blocks with the right error, refund-on-generation-failure actually refunds (the code explicitly implements this per the earlier investigation — worth protecting), and the 24h regen cooldown boundary. **~8-10 test cases, ~200-280 LOC** (this file is the largest and most branchy of the six, hence the wider band).
5. **GDPR delete** (`apps/web/app/api/gdpr/delete-account/route.ts`, 101 lines + `apps/web/app/api/cron/cleanup-deleted-accounts/route.ts`, 192 lines — 293 total). Risk is legal, not just functional: a bug here either fails to delete on request (GDPR non-compliance) or deletes too early/too broadly (data loss, possibly of a paying user). Minimum: POST sets the grace period correctly, DELETE (cancel) reverses it, the double-request guard (409) fires, and the cron's cascade actually removes rows from every table it claims to (test against a seeded fixture spanning the 10+ tables the cron touches, not just a mock). **~8-10 test cases, ~200-260 LOC** — this one is worth the higher end of its band because the cascade's correctness can't be meaningfully asserted without real seeded rows across every touched table.
6. **Rate limiting** (`apps/web/lib/rate-limit.ts`, 50 lines). Lower LOC, still worth covering given §3/§4 flagged it as under-applied: the core RPC-backed increment/check logic, the fail-open behavior on limiter error (verify it fails open, not closed — an accidental fail-closed here would take down an endpoint under a transient Supabase blip), and the 429 response shape. **~4-6 test cases, ~80-120 LOC.**

**Total band: ~42-56 test cases, ~1,100-1,490 LOC**, against a 1,654-line base of the highest-risk source files identified. This is deliberately narrower than "test everything" — it covers the six areas named in the request (money, quota, deletion, chart correctness, abuse protection) and explicitly excludes UI component tests, the Кръг compatibility-math layer (lower risk — pure functions, already exercised indirectly by real usage, and Circle is pre-revenue), and end-to-end click-through coverage. Mocking Supabase/Stripe/RevenueCat clients is the main setup cost not reflected in the per-area LOC bands above — budget an additional **~150-250 LOC** for shared test fixtures/mocks used across all six areas, bringing the realistic total to **~1,250-1,740 LOC**.

**Decision (2026-08-04): build areas 1 and 2 now (Stripe + RevenueCat webhooks), defer areas 3-6 until after the Кръг port.** Reasoning given: those are the two paths where a silent failure takes money and delivers nothing in return, RevenueCat has never been tested end to end at all (unlike Stripe, which at least has the manual-verification fast path noted in §1), and both are pure server-side logic verifiable without a device or a deployment. Combined estimate from the bands above: ~500-650 LOC test code + shared fixtures. The Vitest config and mock scaffolding are being set up so areas 3-6 are cheap to add later rather than a second setup cost. See §9.7 for what was actually built.

### 9.4 Apple privacy manifest — resolved

No `PrivacyInfo.xcprivacy` needs to be hand-authored right now, and the earlier "flagged, not resolved" status is closed with a bounded answer, not a punt. `apps/mobile/app.json` has no `ios.privacyManifests` key and there is no `ios/` native directory in the repo at all — this is a fully managed Expo project (`expo prebuild` has never been run), consistent with §6's finding that no EAS build has ever been produced. Because there's no native project, there's also no first-party native code that could be directly calling a required-reason API (UserDefaults, file-timestamp, disk-space, active-keyboard, or system-boot-time) outside of what ships inside the JS-bridged SDKs already installed — grepped `apps/mobile` for any custom native module code and found none; everything goes through Expo/RN modules.

That leaves third-party SDK compliance, which is the actual open question. Four installed dependencies plausibly touch required-reason categories: `@sentry/react-native` (~7.2.0) uses UserDefaults and file-timestamp APIs for breadcrumb/session persistence; `@react-native-async-storage/async-storage` (2.2.0) uses UserDefaults for small-value caching; `react-native-purchases` (RevenueCat, ^10.6.0) uses UserDefaults to cache customer info offline; `@clerk/expo` (^3.2.4) likely touches Keychain/UserDefaults for session storage. All four are recent major versions, well past Apple's May 2024 enforcement deadline — SDK maintainers at this scale (Sentry, RevenueCat, Clerk, the Expo/RN core team for AsyncStorage) have shipped their own bundled `PrivacyInfo.xcprivacy` inside their respective pods/frameworks since then; this is now standard practice for actively-maintained SDKs of this profile, not something Stellaeum's app code needs to author on their behalf. **[inferred, not verified]** — confirming this with certainty requires an actual `expo prebuild` + Xcode archive, which is the same missing step blocking everything else in §6/§7; Xcode's build-time manifest aggregation will surface a missing/outdated declaration from any of the four SDKs automatically if one exists, at zero additional cost, the first time an EAS iOS build actually runs. Recommendation: don't treat this as a separate pre-work item — fold it into acceptance criteria for the first EAS iOS build (§ next-work item 1): if Xcode's archive step or App Store Connect's binary processing flags a missing manifest, it will name the exact SDK, at which point it's a one-line `app.json` `ios.privacyManifests` addition or an SDK version bump, not a research problem. This is now a bounded, cheap tail risk rather than an open question.

### 9.8 EAS build investigation — what's possible before Apple enrollment

Investigated, not built — no `eas.json` was created and no `eas` command was run, since EAS builds are tied to a real Expo account (`eas login`) that only the founder can authenticate, and a cloud build against real project infrastructure isn't something to trigger without that authentication in hand.

**Direct answer: yes, an Android development build can be produced today with zero Apple involvement, and it does not require installing the Android SDK locally either.** EAS's cloud build service builds Android APKs entirely on Expo's own infrastructure — the only local requirements are Node (already present) and `eas-cli` (not yet installed; `npx eas-cli` works without a global install). This machine has no Android SDK, no `adb`, and Java 1.8 (too old for a modern Gradle/RN build) — so a fully *local* `expo run:android` build is not available today without a separate Android Studio + JDK 17 setup. That local-toolchain gap is irrelevant to the recommended path, though, because EAS cloud build sidesteps it entirely: nothing about it depends on Apple Developer status, and nothing about it depends on this machine having Android build tools.

What's confirmed present and absent in the repo right now: `apps/mobile/app.json` already has a valid Android `package` (`com.stellaeum.app`) and no Apple-specific fields are required for an Android profile. What's confirmed missing: `eas.json` (no build profiles defined at all — this is the actual gap, not Apple enrollment), and `expo-dev-client` is not installed as a dependency, which matters only if the founder wants a true "development" build profile (hot-reload against a running Metro bundler); a "preview" (or Expo's "internal distribution") profile produces a fully standalone, installable APK without needing `expo-dev-client` at all — closer to what "a real device build to test against" actually calls for, since it doesn't require a laptop running Metro nearby.

Concrete next steps, in order, all Android-only and Apple-independent:
1. `npx eas-cli login` (free Expo account — create one if none exists; this is separate from and unrelated to Apple Developer enrollment).
2. `npx eas-cli build:configure` — generates `eas.json` with default `development`/`preview`/`production` profiles and links the project to an EAS project id (writes into `app.json`).
3. Add `expo-dev-client` to `apps/mobile/package.json` only if the `development` profile is wanted; skip it for a `preview`-profile build.
4. `npx eas-cli build --platform android --profile preview` — builds on Expo's servers (no local Android SDK needed), returns a downloadable/installable APK link when done (typically several minutes, not instant).

This gives the founder a real device build today, independent of the Apple Developer enrollment timeline — the iOS side of EAS setup (equally worth scaffolding via `eas.json`'s `ios` profile block, but not buildable to a real device until Apple enrollment completes and a distribution certificate/provisioning profile exist) can follow once enrollment clears without blocking the Android path in the meantime.

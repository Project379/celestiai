## Discipline patterns — codified at P.3 close

**Mobile overlay pattern (absolute View + Pressable backdrop + BackHandler):**
The default mobile overlay pattern is absolute-positioned View + Pressable backdrop + `BackHandler.addEventListener('hardwareBackPress', ...)`. **RN Modal is NOT the default.** Precedents: P.2-d NatalWheelLegend (legend tooltip), P.3-c EventModal (transit detail). If a future surface requires RN Modal specifically — focus-trap accessibility, scrollable inner content with gesture conflicts against backdrop, or framework-level modal semantics required by a third-party library — surface as halt-trigger with concrete justification. Founder ratifies pattern exception case-by-case. Rationale: RN Modal introduces Android hardware-back + Expo Router navigation-stack interaction risk; the absolute-View pattern has known semantics across the codebase and integrates cleanly with the existing BackHandler subscriptions.

**Ratified exception — full bottom sheets (2026-07-23):** The rule above governs popovers, tooltips, and inline overlays (NatalWheelLegend, EventModal, CrystalDetailPanel — all "popover-class": anchored to a trigger, partial-screen). It does not fit **sheet-class** surfaces: full slide-up bottom sheets or focused-content takeovers where native slide animation and focus trap are the actual desired behavior, not overhead. `PlanetDetail.tsx` (Карта's planet-tap detail) is the ratified precedent for this class — RN `Modal` stays, with `onRequestClose` wired to the close handler (verified) so Android hardware-back is covered without a hand-rolled `BackHandler`. Future sheet-class surfaces may cite this precedent directly rather than re-litigating the popover-class rule; anything ambiguous between the two classes still halts for founder ratification.

**Cohesive UI batch exception — refined with ~500 LOC ceiling:**
The cohesive UI batch exception to the 250-LOC commit guideline (codified at P.4) applies WHEN:
- Sub-components share lifted state (props from a single parent state hook)
- Components are co-located in the user's mental model (one visual region)
- Splitting would require duplicating state plumbing

It does NOT apply when:
- Sub-components are co-located only by file proximity, not by state coupling
- Components can be lifted to a different visual region without UX degradation
- Bundle exceeds ~500 LOC even with the coupling — very large bundles indicate genuine multi-concern regardless of state shape

**Ceiling: ~500 LOC.** Above this, the batch must split even if state-coupled. Founder ratifies case-by-case for borderline (450-500 LOC) bundles. Precedents: P.4-c1 (422 LOC, ratified ship-as-batched), P.3-b (383 LOC, comfortably under), P.3-c (445 LOC, ratified at HT 7 with the explicit 500-ceiling commitment).

## Discipline patterns — codified at P.4 close

**Cohesive UI batch exception to the 250-LOC commit guideline:**
The 250-LOC guideline (per `feedback_budget_overrun_discipline.md`) applies to commits >400 LOC with multiple DECOUPLED concerns. **Cohesive UI batches — where component A depends structurally on component B's state, and shipping A without B produces a half-feature — are exempt.** Precedent: P.2-b shipped ChartView tab switch + AstrologyReference at ~468 LOC (tab switch has no value without the reference view), and P.4-c1 shipped route + DiaryContent + EntryForm at 422 LOC (Form consumes DiaryContent's phase + entryCountForPhase derivation). Splitting these fragments cohesion without LOC reduction. Founder ratifies cohesive-batch exemption case-by-case at investigation; the decision criterion is "does the smaller commit ship a usable feature on its own?" If no, the batch ships together.

**Drop framer-motion entry animations on data-display screens:**
Mobile arrival animations are reserved for hero/sigil/wheel-class surfaces only (P.1-e sun sigil, P.2-e wheel arrival). **Data lists, forms, modals, and history surfaces ship without entry animations.** Web's `fadeUp` variants, `AnimatePresence` height transitions on collapsible rows, and section-stagger reveals are dropped on mobile parity ports. Rationale: (a) Conservative SDK defaults posture — entry animations are bundle-cost without gameplay-relevant feedback on read-heavy surfaces, (b) RN's Reanimated worklets have higher integration cost than framer-motion's React-side animation, and the cost-benefit favors saving worklets for headline arrivals. Precedent: P.4-c1 ManifestDiaryContent dropped fadeUp on three sections + error banner AnimatePresence; P.4-c2 ManifestHistory dropped the row-expand height transition (caret rotation kept as visual cue only).

**Amendment, ratified 2026-07-24 (premium pass) — the REVEAL exception:** the rule above still bans entry animations on data-display screens as a *default*. It does not ban them on every surface those screens might contain. **Exception: a REVEAL — a surface whose content is deliberately concealed until a user action discloses it, where the disclosure is the interaction's purpose rather than incidental rendering.** This is narrower than an earlier draft of this exception ("a once-daily surface"), which was rejected as too loose — frequency alone doesn't distinguish a genuine reveal from an ordinary card that simply happens to update once a day, and a frequency-only carve-out invites future surfaces to claim it by analogy rather than by mechanic. The distinguishing test is the mechanic: does the surface exist to conceal-then-disclose, or does it just render data? **Currently this covers the daily crystal draw only** (`CrystalOfTheDayCard.tsx` — see the premium-pass proof surface). The original rationale (a)/(b) above doesn't transparently apply to a reveal the way it applies to a list: a reveal fires once per user action, not on every render of a read-heavy, constantly-rerendering surface, so the SDK-cost and worklet-integration-cost arguments that justify the general ban don't carry over unmodified. **Any future surface claiming this exception requires founder ratification — frequency alone does not qualify a surface, and this is not a standing invitation to reintroduce entry animations wherever a plausible reveal-shaped argument can be constructed.**
